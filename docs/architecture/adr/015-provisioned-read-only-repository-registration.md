# ADR 015: Provisioned read-only repositories and confined inventory

Status: implemented; local tests recorded separately. Independent security review pending.

The local operator provisions a read-only repository parent directory. The authenticated console submits only a bounded asset identifier, `app_demo`, and an explicit read-only acknowledgement. It cannot submit a filesystem path, clone URL, credential, command, script, environment setting, or scanner argument. The bundled demo mounts only the two scanner fixture directories read-only into the controller. Neither the gateway, deployer nor verifier receives the source mount. No Docker socket is added.

Provisioned mounts bind durably to the sole enrolled owner before the first source read. Later accounts cannot connect or list those mounts. Repository IDs, application maps and map history also require the owning account. Multi-owner mount provisioning requires an explicit ACL design; it is not inferred from possession of a path or repository ID.

A shared non-executing Go module supplies inventory to Alpha and the controller. An `os.Root` directory handle confines filesystem traversal. Symlinks are rejected; rooted reads prevent outside-root traversal even if a validated file is subsequently replaced. Unix file opening is nonblocking, followed by regular-file, inode, size and modification checks, so a FIFO replacement does not hang the worker. Reads are byte-bounded even if a file grows. Directory enumeration is chunked and capped before sorting. Source scripts, git hooks, package managers and dependencies are never executed.

Bounds: 1 MiB per file, 64 MiB included input, 10,000 file references, 20,000 directory entries, 64 directory levels and 512-byte paths. The native source reader is currently supported on Linux and macOS; other native platforms refuse execution. The container reader runs on Linux. The API currently requires the full map to fit 60,000 JSON bytes; it refuses a larger map rather than dropping files silently. Storage permits 100 repositories per owner, 100 map versions per repository and 16 MiB of application-map documents total. These are explicit preview limits, not claimed support for large monorepos.

Maps store file references/hashes, source mount identity, observation time, bounded conventional `.git` commit metadata, versioned extractors, declared route facts, and unknowns. Raw source content is not stored. Protected environment/key files and generated directories are omitted. Commit metadata is parsed as data without executing git; external gitdir/worktree metadata is unsupported. Content identity excludes observation time so an unchanged reconnect remains stable. A commit reference does not establish a clean checkout. Rooted reads are not a filesystem-wide immutable snapshot; future scanner execution must capture/revalidate the exact source snapshot rather than scan a changing host tree.

Migration 3 adds repositories and immutable application-map history without modifying prior migration checksums. Reconnect preserves repository identity and records changed map content. Authorization audit and repository/map updates commit together. Read-only mount ownership binding is separately durable and audited, even if the subsequent source inventory fails.

Acceptance includes HTTP unknown-field/path/URL/consent rejection, second-owner denial, file replacement by an escaping symlink, file growth, FIFO replacement, malicious lifecycle scripts, conventional commit identity, root Next.js route recognition, deterministic content hashes, map history/capacity rollback, UTF-8 byte quotas and existing controller regressions. Live container acceptance checks the read-only bind mount, rejects an actual write attempt and compares actual file hashes. It does not establish independent release review.

Remaining: other app registration, private per-owner mount ACLs, remote read-only cloning, immutable scanner snapshots, asynchronous inventory for larger inputs, deletion/retention controls, full framework/auth/ORM extraction, durable scanner jobs and independent security review. Source files and tool output remain untrusted data, never instructions granting authority.
