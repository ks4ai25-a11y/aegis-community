# ADR 028: Durable owner-bound scanner receipt ledger

Status: accepted for the internal controller component. The transport ingest endpoint and worker execution loop remain unfinished.

Scanner workers must write normalized evidence through the controller, not access its database. Migration 7 adds an append-only receipt ledger keyed by job/tool, with owner, request identity, content digest, protected document and ingestion timestamp. Deployed migrations 1–6 are unchanged. Update/delete triggers refuse application-level mutation; this is a local controller/host trust boundary, not protection against a host administrator changing the database or schema.

`Queue.RecordReceipt` is the internal controller ingest operation. A new write checks the durable owner/job/request, dispatch worker and hashed lease capability, active enrollment/mount authority, live uncancelled lease, current repository/map/lock identity and trusted startup pin metadata. It validates/normalizes the receipt using ADR 027 and the job's selected tools and timeout. Startup pin metadata and the lock digest come from the same bounded validated file read; browser/worker inputs cannot select pins.

The hashed canonical document includes owner, job and request identity as well as the normalized execution. This prevents identical zero-finding tool outputs in separate owner/job namespaces from sharing an evidence identity. A job has at most one receipt per selected tool. A conflicting result cannot overwrite an earlier receipt. Accepted structured provenance remains T0/suspected. Free presentation text is discarded, and unproven OSV/Trivy database freshness remains `completed_stale_db`.

Receipt insertion and its audit event commit in one transaction. Audit records identify the tool, receipt/request digest, status and finding count while explicitly recording that cleanup is not independently confirmed. An audit failure rolls back the receipt. Receipt acceptance does not update job state, renew execution authority, complete the suite, assert verified protection or release dispatch admission.

An exact normalized replay checks the original dispatch capability and still-active enrollment, then compares immutable document identity. It may replay a committed receipt after lease expiry, restart or operator pin rotation without authorizing another tool run. Historical map data and originally validated stored pin metadata supply the replay context. Changed timestamps, outputs, provenance or identity are refused; replay does not duplicate audit events. Revoked enrollment cannot replay. New writes still require the live current job authority.

Owner-bound reads first resolve the owner's job, return at most six sorted records, and check stored bytes against their digest plus owner/job/request/tool relations. An unauthorized owner cannot discover a receipt by supplying another owner's job ID. The ledger is bounded to 6,000 records and 64 MiB globally; a full ledger refuses new writes before insertion. Audited archive/retention rotation remains unfinished and must preserve evidence before reclaiming this append-only store.

Tests cover restart/expiry/pin-rotation replay, conflicting replay, cross-owner reads/writes, invalid request/capability/pin/tool/snapshot identity, expired new writes, update/delete refusal, atomic audit rollback, stored digest/relational checks and byte-budget admission. A version-six upgrade test preserves prior worker/state data and migration checksums without inventing receipts. Existing dispatch-preservation upgrade checks also cover the new migration. A component integration obtains a real six-tool controller claim using the actual startup pin loader, parses all six adapter fixtures, persists/replays each through the controller ledger, reads six owner-bound records and confirms the job still remains running. Its container/guard fields are synthetic worker claims; no scanner image is executed.

The local upgrade uses a protected online SQLite backup, initializes the new schema first, and replaces every service sharing the controller image. Local doctor, repository, private-worker and scoped crash/recovery journeys verify continuity. No synthetic receipt is injected into the live owner database to manufacture scan success.

Required next work is authenticated bounded transport ingestion, actual worker receipt submission, independent cleanup confirmation/release, terminal suite aggregation, owner scanner API/UI, retention rotation, deployed scan acceptance and the remaining v4 release requirements. This internal ledger is not a completed scanner workflow.
